# 产品与技术方案

文档状态：开发基线草案，完成 B0 票样白名单后转为正式基线
核查日期：2026-08-13
适用阶段：Android/iOS V1 无自有服务器版本；V1.1 至 V1.5 见独立路线图；Windows/macOS 独立排期

## 1. 项目结论

本项目可以走通。首版闭环为：

```text
拍照、导入单张纸质彩票图片或手动输入
→ 图片路径完成本地质量检测、OCR 和解析；手动路径直接录入结构化字段
→ 用户核对并确认关键字段
→ 按彩种和期号查询官网开奖 JSON
→ 本地规则引擎计算奖级与税前奖金
→ 展示中奖测算结果及数据来源
```

第一版无需自建服务器。图片、OCR 文本、投注号码和规则计算均留在设备上；查询开奖时只发送彩种和期号。

“无自有服务器”不等于“完全离线”。每次测算对应期开奖数据都需要联网。V1 只在当前测算流程的页面状态中保留查询结果，离开流程即清除，不提供缓存或离线复查。

## 2. 产品定位与边界

### 2.1 产品定位

面向持有纸质超级大乐透或双色球彩票的用户，通过图片识别或手动录入票面信息，并结合官方开奖数据完成辅助中奖测算。

产品内统一使用以下表述：

- 中奖测算
- 根据已确认的票面信息和开奖数据计算
- 结果仅供核对，以发行机构公告和实体彩票兑奖结果为准

不得使用以下未经授权的表述：

- 官方验奖
- 彩票验真
- 确认可兑奖
- 确认未撤单、未作废或未兑奖

V1 最终发布范围：

- 平台：Android 和 iOS；Windows、macOS 不属于 V1 发布与验收范围。
- 彩种：超级大乐透、双色球。
- 规则期号：大乐透 `26014` 期及以后；双色球 `2026014` 期及以后。
- 票据：单张、完整、可读的电脑打印纸质票。
- 期数：支持 1 至 20 期连续票；多期仅开放同一年度中段、可由票面起始期号安全连续展开的序列。
- 投注：单式、同一张票上的多注单式、倍数。
- 大乐透：支持基本投注和追加投注。
- 图片采集：Android、iOS 支持应用内拍照和系统图片导入。
- 手动采集：Android、iOS 支持不使用图片直接录入全部必要票据字段。
- Android、iOS 均支持本地 OCR、人工校正、开奖查询和中奖测算。

V1 明确不支持：

- 复式、胆拖、超过 20 期的连投票，以及需要跨年度期次日历才能安全展开的多期票；补打票仅在全部字段与金额闭环成立时放行。
- Windows、macOS 客户端正式发布；现有工程与 OCR 底座作为后续版本基础保留。
- 大乐透 `26013` 期及以前、双色球 `2026013` 期及以前的奖级计算。
- 手写票、严重褪色或破损票、电子彩票截图、多票拼图。
- 未列入支持白名单的省份、销售终端或票面版式。
- 从二维码确认彩票真伪、撤单状态或兑奖状态。

### 2.3 桌面端排期说明

Windows 和 macOS 已完成宿主、系统图片导入、ONNX Runtime 无遥测工作进程和 PP-OCRv5 模型供应链底座，但不进入 V1 发布范围。桌面真实 OCR、ZXing、Windows 实机、目标平台裁剪、签名与分发使用独立路线图另行排期，不占用已经冻结的移动端 V1.1 至 V1.5 版本号，也不影响 Android/iOS V1 完成和验收。桌面摄像头仍需在桌面版本内单独评估。

### 2.4 V1 非功能目标

- 关键字段未经用户确认，不能输出中奖或未中奖。
- 网络失败、接口空数据、未知规则或未知票型，不能输出未中奖。
- 图片默认不上传、不持久化、不进入日志和埋点。
- 支持的历史规则和票型必须有自动化测试。
- UI 必须明确展示开奖来源、期号、获取时间和结果状态。
- 每次网络查询必须由用户操作触发，不进行后台抓取、全量同步或定时轮询。

### 2.6 页面清单

V1 最小页面：

1. 首页：Android/iOS 提供拍照、导入图片和手动输入三个主操作。
2. 拍照页：仅 Android/iOS，包含预览、拍摄、闪光灯和重拍。
3. 图片检查页：展示裁切结果和图片质量问题。
4. 分析进度页：展示可取消的本地分析状态。
5. 票面确认页：图片路径提供原图与结构化字段对照，手动路径提供空白结构化字段录入，二者完成相同的人工确认和领域校验。
6. 开奖查询状态页：展示当前期号、数据源和错误恢复操作。
7. 测算结果页：逐注结果、整票汇总、开奖信息、来源和免责声明。
8. 关于与隐私页：数据处理说明、支持范围、版本和官方联系方式。

V1 不做账号、云同步、社区、选号、购彩、推送、营销首页或排行榜。

### 2.7 后续版本路线

V1、V1.1 与 V1.2 已按个人自用基线关闭，当前稳定版本为 `1.2.0 (4)`；V1.2 已完成合法随机号码、会话内方案管理，以及可承载后续版本的响应式一级导航。V1.3 至 V1.5 依次规划历史走势与数学预测、AI 历史数据分析，以及 AI 传统文化娱乐推演，仍需逐版单独立项；其中 V1.3 在历史开奖数据授权解决前不得发布。详细范围、依赖、验收标准和隐私边界见《[V1 至 V1.5 版本规划](05-version-roadmap.md)》。后续版本不得降低 V1 的人工确认、官方证据和失败关闭标准。

## 3. 用户流程

### 3.1 主流程

1. Android、iOS 用户选择“拍照”“导入图片”或“手动输入”。
2. 图片路径检查图片是否完整、清晰、方向正确且只包含一张票，然后完成本地 OCR、版式解析和字段校验；手动路径直接进入空白结构化录入。
3. 两条路径汇合到同一票面确认和领域校验流程。
4. 应用进入确认页；图片路径展示原图和结构化票面信息，手动路径展示结构化录入内容。
5. 用户修正并确认彩种、起始期号、投注期数、投注类型、号码、倍数和追加属性；不支持的票型或期次序列在确认前明确阻断。
6. 应用先检查期号是否落在已验证规则范围；不支持时停止并说明原因。
7. 应用按彩种和精确期号查询官网数据源；多期票按时间顺序逐期查询，用户可以主动重试未完成期次。
8. 应用验证开奖数据完整性并选择对应规则版本。
9. 规则引擎逐注、逐期计算最高奖级；只有全部期次结论和金额完整时才汇总整票税前奖金。
10. 应用展示中奖、未中奖或暂时无法判断，并给出具体原因。

### 3.2 人工确认要求

V1 始终显示一次票面确认页，不启用完全自动放行。确认页至少支持：

- 彩种选择。
- 期号编辑与格式校验。
- 投注类型选择。
- 红球/蓝球或前区/后区号码球选择器。
- 倍数和 1 至 20 期连续投注期数步进器；无法安全展开的多期序列标记为 `UNSUPPORTED_TICKET`。
- 大乐透追加开关。
- 低置信度字段定位到对应图片区域。
- 票面金额与结构化投注金额的差异提示。

用户修改后的字段标记为“人工确认”。网络返回的开奖结果不得静默改写用户确认的票面字段。

### 3.3 结果状态

识别状态：

- `READY_FOR_REVIEW`：识别完成，等待确认。
- `NEEDS_CORRECTION`：存在低置信度或不合法字段。
- `POOR_IMAGE`：图片模糊、过曝、严重倾斜、明显透视或裁切。
- `UNSUPPORTED_TICKET`：票型或版式不在支持清单。
- `RECOGNITION_FAILED`：OCR 或解析失败。

开奖状态：

- `NOT_PUBLISHED`：对应期次尚无官方数据。
- `PUBLISHING`：数据不完整或仍在发布中。
- `FINAL_NUMBERS`：号码稳定，当期规则和特别政策状态可确定，允许判断是否中奖和奖级。
- `FINAL_PAYOUT`：奖级单注金额和附加奖金也完整，允许显示确定的税前测算金额。
- `NETWORK_UNAVAILABLE`：当前无法联网查询开奖数据。
- `SOURCE_UNAVAILABLE`：官方接口异常或结构变化。
- `CONFLICT`：同期开奖数据与公告校验不一致。

测算状态：

- `NOT_CALCULATED`：尚未计算。
- `WIN`：至少一注中奖。
- `NO_WIN`：所有投注均完成计算且均未中奖。
- `RULE_UNSUPPORTED`：对应期号或玩法没有已验证规则。
- `NEEDS_MANUAL_REVIEW`：输入或开奖证据不足。

只有票面关键字段已确认、开奖状态至少为 `FINAL_NUMBERS`、票型和规则均受支持、所有投注均计算成功时，才允许输出 `NO_WIN`。中奖但开奖金额尚未完整时，可以输出奖级，金额显示“待官方数据确认”。

## 4. KMP 总体架构

### 4.1 目标平台

- Android：Kotlin Android target。
- iOS：Kotlin/Native `iosArm64`、`iosSimulatorArm64`。
- Windows/macOS：同一个 JVM `desktop` target，分别构建和发布。
- UI：Compose Multiplatform。

项目不以共享率为验收指标。共享领域规则、数据访问、状态管理和大部分 UI；相机、图片选择、文件目录、OCR 引擎和签名发布保留在平台层。

### 4.2 模块划分

本仓库于 2026-08-25 核对 [JetBrains Kotlin Multiplatform 官方共享 UI 模板](https://www.jetbrains.com/help/kotlin-multiplatform-dev/compose-multiplatform-create-first-app.html)，采用独立平台宿主与 `shared` 共享模块的当前命名。旧模板中的 `composeApp` 并非错误，但已经迁移为 `:shared`；迁移不改变 Kotlin 包名、iOS framework 名或业务行为。官方模板中的 `webApp` 是可选宿主，本项目当前没有 Web 目标，不为结构对齐引入无用模块。

```text
:androidApp
:desktopApp
:shared
:shared:domain
:shared:data
:shared:persistence
:shared:recognition
iosApp/（Xcode 工程，不是 Gradle 模块）
```

`:androidApp`：

- Android Application 宿主、清单、图标、版本、签名和 R8 配置。
- 依赖 `:shared` 并启动共享 Compose UI。

`:desktopApp`：

- Windows/macOS JVM 宿主、原生分发配置和桌面进程入口。
- 依赖 `:shared`；为受控 ONNX Runtime 子进程额外直接依赖 `:shared:recognition`。

`:shared`：

- 共享 Compose 页面、状态持有者和应用装配。
- 通过 `commonMain` 共享业务流程，通过平台 source set 实现相机、选图、文件、网络和能力工厂。
- 产出供 iOS 宿主嵌入的静态 `Shared.framework`。

`:shared:domain`：

- 彩种、期号、号码、投注、开奖、奖级和金额模型。
- 双色球、大乐透规则引擎。
- 规则版本选择器和中奖测算用例。
- 纯 Kotlin，不依赖 Compose、Ktor 或数据库。

`:shared:data`：

- Ktor 客户端和体彩、福彩源适配器。
- DTO 到领域模型的映射与完整性校验。
- Repository、当前流程数据状态和刷新策略。
- 上游 DTO 不得泄漏到领域层。

`:shared:persistence`：

- Room 3 实体、DAO、数据库工厂、显式迁移和模式导出。
- 结构化票据的事务读写、跨平台逻辑导入导出与完整性校验。
- 只依赖领域模型，不保存票图、OCR 全文或官网原始响应。

`:shared:recognition`：

- OCR 标准结果模型。
- 图片分析编排接口。
- 票面文字归一化、版式解析、候选值与置信度。
- 具体 OCR、图像解码和预处理位于各平台 source set。

`iosApp/`：

- Xcode 宿主、签名配置、Info.plist 和 Compose ViewController 入口。

依赖方向：

```text
:androidApp / :desktopApp / iosApp
                  ↓
               :shared
          ↙       ↓        ↘
       data   persistence   recognition
          ↘       ↓        ↙
             :shared:domain
```

`:shared` 同时直接依赖 `:shared:domain`。所有业务子模块保持指向领域层的单向依赖，领域层不反向依赖 UI、网络、数据库或 OCR；Desktop 的工作进程依赖是宿主打包需要，不改变业务依赖方向。

第一版采用构造注入和轻量 `AppContainer`，不提前引入 DI 框架。

### 4.3 核心接口

公共层使用小接口隔离平台和上游变化：

```kotlin
interface ImageAcquirer
interface ImageQualityAnalyzer
interface TicketRecognizer
interface TicketParser
interface DrawRepository
interface PrizeCalculator
interface AppPaths
```

优先通过接口和构造注入提供平台实现。`expect/actual` 仅用于很薄的路径或能力工厂。

大图和相机连续帧不得放入 Compose State，也不得持续跨 Kotlin/Native 边界。平台先把图片复制到应用私有临时目录，公共层只传递 `ImageRef` 和元数据，分析结束后清理临时文件。

## 5. 图片采集与 OCR

### 5.1 平台方案

| 平台 | 拍照/导入 | OCR | 条码辅助 |
|---|---|---|---|
| Android | CameraX、Photo Picker | PP-OCRv5 mobile + ONNX Runtime Android | 后续评估 |
| iOS | AVFoundation、PHPicker | PP-OCRv5 mobile + ONNX Runtime Swift | 后续评估 |
| Windows | 系统文件选择器 | PP-OCR 轻量模型 + ONNX Runtime Java | ZXing |
| macOS | 系统文件选择器 | PP-OCR 轻量模型 + ONNX Runtime Java | ZXing |

首版承诺 JPG、JPEG、PNG。桌面 JVM 默认无法可靠解码 HEIC；HEIC 作为后续兼容项单独评估。移动端捕获统一归一化为 JPEG。

云 OCR 不进入首版。客户端直连云 OCR 会暴露密钥并上传敏感彩票图片。

### 5.2 PP-OCRv5 模型供应链与运行时

移动端与桌面工程底座共用以下有官方来源的模型组合；移动端运行流水线已经接入，真实票准确率和发布验收仍未完成：

- PaddleOCR 仓库 `v3.7.0` 的 PP-OCRv5 mobile 三段模型：`PP-OCRv5_mobile_det`、`PP-LCNet_x0_25_textline_ori`、`PP-OCRv5_mobile_rec`。
- 识别字典使用同一版本的 `ppocr/utils/dict/ppocrv5_dict.txt`，当前为 18,383 行；字典顺序必须与模型一致，不得自行删减或重排。
- 官方发布的是 Paddle 推理模型，不是 ONNX。使用 Paddle2ONNX `v2.1.0` 转换，PoC 固定转换命令、opset、转换日志、源文件和 ONNX 文件 SHA-256，并执行 ONNX checker 和金样本输出对比；禁止使用来源不明的社区 ONNX。
- 仓库通过 `model-lock.json` 同时向转换工具和 JVM 运行时提供单一模型锁，固定 macOS arm64、Python `3.9.6`、PaddlePaddle `3.0.0`、ONNX `1.17.0`、opset 17、关闭自动升级并明确禁用外部优化器；普通 Gradle 构建不联网下载模型，转换产物只有哈希完全一致才允许进入后续分发验证。
- JVM 推理候选为 `com.microsoft.onnxruntime:onnxruntime:1.29.0` 的 CPU 执行提供器。官方 JAR 已核实包含 Windows x64 和 macOS arm64 原生库；B3 必须验证 Compose 打包、签名、公证以及是否剔除无关平台原生库。
- Android 使用 `com.microsoft.onnxruntime:onnxruntime-android:1.24.2` 官方 AAR；模型从 APK 资源复制到 `noBackupFilesDir` 前后核对长度和 SHA-256，再按进程复用三段 CPU Session。Desktop `1.29.0` 不与移动制品混用。
- iOS 使用微软官方 ONNX Runtime Swift Package `1.24.2`；Swift 只负责连续 Float32 张量和 Session，检测、方向分类、识别预后处理及 CTC 解码全部复用共享 Kotlin。模型和字典位于签名应用 Bundle，构建产物必须逐项核对哈希。
- 该版本官方 `Privacy.md` 明确说明受支持平台的官方二进制默认开启遥测。项目必须在原生库初始化前设置 `ORT_DISABLE_TELEMETRY=1`，或改用通过 `--no_telemetry` 构建并完成供应链记录的目标平台制品；只在初始化后调用关闭 API 不满足本项目的本地处理边界。Windows/macOS 产品启动器完成并验证该约束前，不得启用真实桌面 OCR。
- Desktop PoC 采用独立本地工作进程隔离 ONNX Runtime：普通 UI 主进程不加载运行时，父进程在创建子进程时注入 `ORT_DISABLE_TELEMETRY=1`，子进程随后再次调用关闭遥测 API。运行时健康检查协议只返回版本和执行提供器，拒绝额外输出；macOS arm64 分发启动器已通过该路径，Windows x64 仍需在实际分发包中验收。
- 三份转换后 ONNX 合计约 21.3 MB。Android 通用 Debug APK 还会包含四套 ORT ABI，当前约 140 MB；正式 AAB 按设备 ABI 拆分后的下载体积、iOS 包体和目标平台裁剪只能以发布构建实测为准。
- 模型随安装包离线提供，运行时不联网下载；加载前校验版本和 SHA-256。
- PaddleOCR、模型和 Paddle2ONNX 使用 Apache-2.0，ONNX Runtime 使用 MIT。发行包必须附带许可证正文、第三方声明、模型来源、版本、哈希和转换说明。
- Android 历史开奖公告使用 Apache-2.0 的 PDFBox Android `2.0.27.0`；只启用未加密文本层能力并排除 BouncyCastle 传递依赖。发布材料仍须加入 PDFBox Android 与上游 Apache PDFBox 的许可证和第三方声明，且只能处理严格官方域名、固定结构和受限大小的公告。

### 5.3 分析流水线

```text
读取原图及 EXIF 方向
→ 图片质量检测
→ 彩票边缘检测、旋转和透视校正
→ 生成原始校正图和增强候选图
→ 全票中文 OCR
→ 号码区域高分辨率 OCR
→ 条码辅助识别
→ 票面结构解析
→ 领域约束校验
→ 字段置信度聚合
→ 用户确认
```

图像质量检测至少覆盖模糊、过曝、阴影、反光、分辨率不足、严重透视和关键区域裁切。预处理可以使用灰度、局部对比度增强、轻度去噪、锐化和自适应二值化，但必须保留原始校正图并比较多个候选结果。

解析采用“标题锚点 + 相对版式 + 领域约束”，不能依赖固定像素坐标。OCR 不得把非法数字静默替换为相近的合法数字。

### 5.4 票面字段模型

至少识别并允许校正：

- 彩种。
- 期号。
- 投注类型；V1 仅接受单式和多注单式，识别到复式或胆拖时标记为不支持。
- 投注号码和号码区域。
- 大乐透是否追加。
- 倍数。
- 期数；V1 接受 1 至 20 期受控连续票，超过上限或跨年度未知序列标记为不支持。
- 票面总金额。
- 销售时间，作为辅助校验。
- 每个字段的原文、归一化坐标、候选值、置信度和人工修改标记。

流水号、销售网点和二维码内容不是中奖测算必需字段，默认不保存。

### 5.5 二维码边界

不同省份和销售终端的二维码可能是明文、URL、交易 ID、校验值或加密载荷。V1 规则：

- 二维码只是辅助输入，不是主识别来源。
- 未公开载荷不做猜测性解码。
- 不自动打开二维码 URL。
- 原始二维码内容不写日志、不上传、不默认持久化。
- 即使解析成功，也不能据此声称彩票真实有效。

只有取得稳定格式、版本标识和充分票样后，才能用二维码交叉校验 OCR。

## 6. 领域数据模型

建议的核心领域对象：

```text
LotteryType
Issue
TicketDraft
ConfirmedTicket
BetLine
SingleBet
MultipleBet
DanTuoBet
DrawResult
PrizeTier
RuleVersion
PrizeCheckResult
SourceEvidence
```

`MultipleBet` 和 `DanTuoBet` 仅作为未排期后续设计占位，不得由 V1 UI、解析器或规则入口创建，也不默认归入 V1.1 至 V1.5。

金额统一使用分为单位的 `Long`，禁止使用 `Float`、`Double` 或容差比较。票面购买金额命名为 `paidAmountFen`，测算奖金命名为 `estimatedPrizeFen`，不得共用含糊的 `amount` 字段。

`DrawResult` 至少包含：

```text
彩种、期号、开奖日期
主号码、次号码
开奖状态、数据修订号
规则版本
奖级明细及当期单注奖金
来源 URL、获取时间、内容哈希
```

`ConfirmedTicket` 必须是不可变对象，并记录字段来自 OCR 还是人工确认。只有 `ConfirmedTicket` 才能进入规则引擎。

### 6.1 V1 票据领域约束

统一约束：

- 单张票只允许一个彩种、一个起始期号和 1 至 20 期连续投注；一张票可以有多行单式投注。
- 同一行号码不得重复；不同行即使号码完全相同，也应按多注计算，不得去重。
- 号码在比较前升序标准化，但保留原始识别文本用于确认页。
- 倍数范围为 `1..99`；识别到 `0`、`100` 或更大值时为无效输入。
- 领域校验状态至少区分 `VALID`、`AMBIGUOUS`、`UNSUPPORTED`、`INVALID`，只有 `VALID` 可以进入奖级计算。
- 单期票只校验期号格式；多期票在接入官方跨年度期次日历前，仅按同一年度前缀和三位期次序号连续展开，末期序号不得超过 120。
- 每个展开后的期号都复用同一组投注行和倍数独立计算一次，不能在单期奖金中再次乘以投注期数。

大乐透单式约束：

- 每行前区恰好 5 个互异整数，范围 `1..35`；后区恰好 2 个互异整数，范围 `1..12`。
- 前后区是不同号码池，数值相同不冲突。
- 基本投注每注 200 分，追加投注每注另加 100 分。
- 单张彩票基本投注金额不得超过 2,000,000 分；基本投注加追加投注金额不得超过 3,000,000 分。
- V1 票样未证明逐行混合基本/追加前，确认页按票面原文解析追加属性；无法确定全部投注的追加归属时返回 `AMBIGUOUS`，不能假定整票统一追加。
- 追加不改变命中矩阵，只影响一、二等奖的追加奖金。追加奖金优先取当期开奖明细的实际单注金额，不能在客户端自行按 80% 取整。

双色球单式约束：

- 每行红球恰好 6 个互异整数，范围 `1..33`；蓝球恰好 1 个整数，范围 `1..16`。
- 每注 200 分，不存在追加字段；双色球输入出现追加属性时为无效输入。
- 单张彩票投注金额不得超过 2,000,000 分。

票面金额校验：

- 已知投注行数、倍数、期数和追加属性时，票面总金额必须与逐行单期价格乘以全部期数的结果严格相等，不使用误差容忍或就近修正。
- 字段缺失时只能通过金额生成合法候选，不得覆盖已经明确识别的字段。恰好一个合法候选时标记为 `DERIVED` 并要求用户确认；多个候选时返回 `AMBIGUOUS`。
- 例如一注大乐透 600 分既可能是基本投注 3 倍，也可能是追加投注 2 倍，应用不能任选一种。
- 非整分、负数、公式不整除或超过官方投注限制的金额均为无效输入。
- 识别到“复式、胆拖、胆、拖”等字样、某区号码数量超过单式数量，或金额无法由单式公式解释时，返回 `UNSUPPORTED` 或 `INVALID`，不得截取前几个号码继续计算。

上述投注金额与倍数限制来自现行官方规则。规则链接见《开奖数据与中奖测算规则》，后续规则版本变化时必须同步版本化，不能作为跨期永久常量。

## 7. 网络与本地状态

### 7.1 网络层

使用 Ktor，在不同平台注入网络引擎：

- Android：OkHttp。
- iOS：Darwin。
- Desktop：CIO 或 JVM OkHttp，项目初始化 PoC 后冻结。

配置要求：

- `ContentNegotiation` 和 kotlinx.serialization。
- `ignoreUnknownKeys = true`、`explicitNulls = false`。
- 连接、请求和 socket 超时。
- 仅对 GET 的瞬时网络错误和 5xx 重试 1 至 2 次。
- 不对业务空结果无限重试，不进行高频轮询。
- 仅在用户确认票面或主动点击重试/刷新后发起查询。
- 不在后台预取历史开奖，不做全量数据抓取。
- 使用系统 TLS，不关闭证书校验，不固定 CDN 证书。

体彩、福彩各自实现适配器，再映射到统一领域模型。按票面明确的彩种和期号查询，不能用“最新一期”猜测。

### 7.2 当前流程状态

V1 不引入数据库，不缓存开奖数据，不保存原始上游响应，也不保存票据或测算历史。理由：

- 当前需求只有即时识别和查询对比，没有历史记录需求。
- 福彩响应明确声明 `no-store`，未获许可前不应设计长期缓存和批量归档。
- 减少四端数据库、缓存一致性和敏感数据生命周期的首版复杂度。

一次查询得到的统一 `DrawResult` 只作为当前测算流程的 UI 状态存在，并且必须：

- 在用户退出、重新开始或流程状态销毁时清除。
- 不包含票图、OCR 全文、流水号或二维码。
- 允许用户主动刷新。
- 刷新得到的内容哈希发生变化时提示用户重新核对，不静默沿用旧结果。

V1.1 已使用跨平台 Room 3 保存用户确认后的结构化票据，支持本机记录二次查询和 Android/iOS 逻辑包导入导出；原始票图、OCR 全文和官网原始响应仍不进入默认持久化范围。V1.3 如需长期保存规范化历史开奖数据，必须先取得数据存储、分析和展示授权。具体边界见《[V1 至 V1.5 版本规划](05-version-roadmap.md)》和 ADR-016。

## 8. 隐私与安全

- 使用系统 Photo Picker/PHPicker，避免申请整个相册权限。
- 彩票图像只进入应用私有临时目录，默认分析完成后删除。
- 查询开奖只发送彩种和期号。
- 日志、崩溃报告和埋点不得包含票面全文、号码、流水号或二维码。
- 不持久化官网原始响应，不进行后台抓取和批量归档。
- 持久化图片前必须删除 EXIF 位置数据；V1 默认不持久化图片。
- 不自动把票图或结构化投注备份到云盘。
- 真实票样优先使用已兑奖、作废或超过兑奖期的彩票，加密保存且不得提交 Git。
- 未获官方授权前，不把官网内部接口描述为开放 API，也不承诺长期稳定。

## 9. 性能与质量目标

指标必须按平台、彩种、票型、版式和拍摄条件分别统计：

- 支持范围内清晰图片的彩种和期号准确率不低于 99.5%。
- 单个号码 token 准确率不低于 99.9%。
- 整张票全部关键字段一次识别完全正确率不低于 98%。
- 不确定关键字段进入人工校正的召回率为 100%，即盲测中不允许任何错误关键字段被自动标记为已确认。
- 用户确认后的领域校验通过率为 100%。
- 规则引擎官方黄金用例通过率为 100%。
- 已确认黄金样本中错误输出“未中奖”的数量为 0。
- OCR 在断网状态下正常运行，网络抓包中票图和 OCR 内容外发数量为 0。
- 12MP 图片分析目标：移动端 P95 不超过 3 秒，桌面 P95 不超过 5 秒；以目标设备实测校准。

未知版式、模糊、裁切或规则不支持的负样本必须被拒绝或要求修正，不能直接进入最终中奖测算。

## 10. 构建与发布

KMP 不产生一个通用安装包，至少需要：

- Android V1：APK/AAB。
- iOS V1：IPA。
- Windows 后续版本：MSI/EXE。
- macOS 后续版本：DMG/PKG。

iOS 必须在 macOS 上构建和签名。Windows/macOS 正式分发要求与对应 runner 在桌面版本恢复开发时验收，不属于移动 V1 发布闸门。

首版建议平台矩阵：

- Android 主流 64 位设备，具体最低版本由 CameraX、ONNX Runtime 和 Compose 兼容性验收后冻结。
- iOS arm64，最低版本由 Compose、ONNX Runtime 和部署要求验收后冻结。
- Windows 10/11 x64。
- macOS Apple Silicon；Intel 支持另行评估。

Windows 正式发布需代码签名以降低 SmartScreen 警告；macOS 站外分发需 Developer ID、Hardened Runtime 和公证。应用商店或官网分发渠道必须在发布批次前冻结。

## 11. 真实票样计划

真实票样是当前最大技术不确定性，不能只靠网络图片或合成数据：

- 探索阶段：每个彩种至少 20 至 30 张不同物理票，覆盖至少 3 个省份和多个终端版式。
- 开发阶段：每个彩种至少 100 至 150 张不同物理票。
- 发布验收：每个彩种建议 150 至 200 张不同物理票，每张至少 3 种拍摄条件，总图片量约 900 至 1200 张。
- 同一物理票的多张照片必须放在同一数据分组，不能跨训练/调参与盲测集。
- 留出 20% 至 30% 的彩票和终端版式作为从未参与调参的盲测集。
- 标注由两人独立录入并复核。
- 合成数据可用于解析器和规则测试，不能替代真实 OCR 验收。

支持白名单不是一句“支持某省”，而是一张可审计表。B0 使用以下模板，未填满必填项或未达到样本门槛的行不得进入 V1 发布范围：

| 彩种 | 省份 | 终端/可辨识特征 | 版式编号 | 票型 | 追加形态 | 物理票数 | 图片数 | 拍摄条件 | 双人复核 | 状态 |
|---|---|---|---|---|---|---:|---:|---|---|---|
| 待采集 | 待采集 | 待采集 | 待编号 | 单期单式 | 基本/追加 | 0 | 0 | 标准/倾斜/弱光 | 否 | 探索 |

白名单准入规则：

- 探索阶段每种彩票至少 20 张不同物理票，覆盖至少 3 个计划发布省份。
- 每个版式至少 5 张不同物理票才能进入开发白名单；最终发布仍需满足盲测规模和准确率要求。
- 同一物理票的不同照片只计一张物理票，不得通过重复拍摄虚增版式覆盖。
- 省份、终端或版式无法辨识时单独标记，不得并入已知版式统计。
- 不能取得票样的省份明确列为不支持，不以“全国通用”作假设。

## 12. 成功标准

V1 完成必须同时满足：

1. Android、iOS 可通过应用内拍照、导入图片或无图手动输入完成闭环。
2. 支持白名单内 1 至 20 期的单式、多注单式、倍数及大乐透追加票能够本地识别并完整人工校正。
3. 两种彩票能按期号取得并校验官方开奖数据。
4. 支持的玩法和规则版本能够准确计算奖级及税前金额。
5. 所有不确定和故障状态均不会误报“未中奖”。
6. 图片和投注内容不会被发送到外部服务。
7. 每个批次的自动化测试、真机测试和票样盲测均达到验收门槛。

## 13. 开发启动条件与上线前置条件

B1 工程开发可以在以下条件满足后启动：

- 用户确认本文档冻结的 V1 范围：Android/iOS 拍照或导图；受控的 1 至 20 期单式、多注、倍数和大乐透追加；桌面发布延期。
- 用户指定首批计划覆盖的至少 3 个省份，并确认可以开始收集已失效或已兑奖实体票。
- B0 为每种彩票取得至少 20 张探索票样并建立白名单；达不到时只允许开展 B1、B2 和通用 OCR 技术 PoC，不承诺自动票面解析范围。

这些输入不阻止确定性的 KMP 骨架和规则引擎开发，但会阻止 B4 票面解析进入发布实现。

技术开发可以先行，但面向公众正式分发前应完成：

- 联系体彩 95086、福彩 954168，确认官网开奖数据调用、缓存和展示授权。
- 完成隐私政策、结果免责声明和应用商店合规审核。
- 对官网接口变化准备更新和降级方案。
- 取得目标省份、玩法和终端的足量真实票样。
- 明确发行渠道、签名证书和支持系统版本。

## 14. 主要风险与应对
