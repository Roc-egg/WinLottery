# 架构与产品决策记录

## ADR-001：产品定义为中奖测算

- 状态：已采用。
- 决策：V1 只根据用户确认的投注信息和开奖数据计算理论奖级与税前金额。
- 原因：官网开奖接口不提供彩票真伪、撤单和兑奖状态。
- 影响：UI、商店文案和免责声明不得使用“官方验奖”或“验真”。

## ADR-002：采用 Compose Multiplatform 四端共享

- 状态：已采用。
- 决策：Android、iOS、Windows、macOS 使用 KMP 和 Compose Multiplatform；Desktop 为 JVM 目标。
- 原因：领域规则、网络、存储、状态和多数 UI 可共享，同时允许平台 OCR 和相机使用成熟原生能力。
- 影响：不会产生一个通用安装包；必须分别构建、测试、签名和发布。

## ADR-003：移动端拍照，桌面首版导入图片

- 状态：桌面发布范围已由 ADR-011 调整，移动端采集决策继续有效。
- 决策：Android/iOS 的 V1 支持应用内拍照和图片导入；桌面系统导入能力已经完成 PoC，但随 Windows/macOS 客户端整体延期。
- 原因：Desktop 没有统一可靠的 KMP 摄像头 API，强行纳入会显著扩大原生依赖和发布风险。
- 影响：桌面摄像头不属于 V1 验收范围，后续需独立 ADR 和开发批次才能纳入。

## ADR-004：OCR 全部本地执行

- 状态：已采用。
- 决策：Android/iOS 使用同一套 PP-OCRv5 mobile 三段 ONNX、字符字典和共享预后处理；Android 使用 ONNX Runtime Android，iOS 使用 ONNX Runtime Swift；Desktop 保留独立 ONNX 工作进程路线；不调用云 OCR。
- 原因：保护票据隐私、避免客户端密钥和网络依赖。
- 影响：移动端模型行为与字符类别一致，但图片解码、运行时版本、硬件和系统差异仍需分别验收；安装包体积明显增加。Desktop 的 ONNX Runtime 只允许在父进程预先禁用遥测后启动的独立本地工作进程中加载。

## ADR-005：所有票面关键字段必须人工确认

- 状态：已采用。
- 决策：V1 不做完全无感自动中奖测算，OCR 后始终进入确认页。
- 原因：热敏票据、不同省份版式和 OCR 数字混淆可能导致严重误判。
- 影响：只有不可变的 `ConfirmedTicket` 能进入规则引擎。

## ADR-006：V1 无自有服务器，使用 Repository 隔离官网源

- 状态：已采用。
- 决策：首版原生客户端通过 Ktor 低频查询官网内部 JSON；网络层隐藏在 `DrawRepository` 后。
- 原因：当前需要先完成本地闭环，两个官网接口现阶段足以按期号查询。
- 影响：接口变化只能通过新版客户端修复；上线前仍需官方授权，未来可无损切换自有 BFF。

## ADR-007：规则按期号版本化

- 状态：已采用。
- 决策：规则选择只基于彩种和期号，命中矩阵、奖金和临时派奖分层。
- 原因：双色球 `2026014`、大乐透 `26014` 存在明确规则切换，历史规则和奖级数量不同。
- 影响：V1 仅支持大乐透 `26014` 起和双色球 `2026014` 起；更早期号返回 `RULE_UNSUPPORTED`，不得套用现行规则。

## ADR-008：V1 不缓存或持久化票图、开奖响应和测算历史

- 状态：V1 已采用；V1.1 的结构化票据持久化由 ADR-016 补充。
- 决策：开奖数据只存在于当前测算流程状态；离开流程即清除。票图使用临时文件并在分析后删除。
- 原因：当前没有历史记录需求，且福彩响应声明 `no-store`，未获许可前不设计长期缓存。
- 影响：V1 关闭应用后需要重新采集票据并联网查询；V1.1 只保存用户确认后的结构化票据，官网原始响应仍不持久化。

## ADR-009：复式、胆拖和多期不进入 V1

- 状态：多期部分已由 ADR-012 取代；复式和胆拖部分继续有效。
- 初始决策：V1 只支持单期、单式、多注单式、倍数和大乐透追加。复式、胆拖和多期均不属于 V1 发布范围。
- 原因：其计算规则可实现，但真实票面编码、金额校验和跨终端版式尚未经过足量票样验证。
- 影响：复式、胆拖和其他未知票型仍必须返回 `UNSUPPORTED_TICKET`；多期票按 ADR-012 的更窄边界处理。

## ADR-010：开奖响应不持久化，开发验证只保留最小证据

- 状态：已采用。
- 决策：正式客户端遵循上游缓存指令，不持久化开奖响应；B2 开发验证只保留响应 SHA-256、规范化必要字段和状态迁移。福彩原始响应只在内存中解析，不写入持久介质。
- 原因：需要验证开奖发布时序和接口字段变化，同时避免把开发审计需求扩展成客户端缓存功能。
- 影响：测试使用人工最小化的同结构契约夹具；采样证据不得进入安装包、Git、产品日志或用户设备，也不得用于后台批量抓取。

## ADR-011：V1 优先发布 Android 和 iOS

- 状态：已采用。
- 决策：V1 发布与验收平台收敛为 Android、iOS；Windows、macOS 客户端使用独立路线图另行排期，不占用移动端 V1.1 至 V1.5 版本号。既有桌面宿主、导图、无遥测 ONNX 工作进程和 PP-OCRv5 模型供应链底座继续保留。
- 原因：移动端相机与本地 OCR 已完成真机纵向链路，能更快验证真实用户流程；桌面真实 OCR、Windows 实机、原生依赖裁剪和分发签名会扩大首版发布风险，且不是验证核心中奖测算价值的必要条件。
- 影响：B3 至 B6 的 V1 闸门只考核 Android/iOS；桌面未完成项不阻塞 V1，但恢复桌面开发时必须重新建立真实 OCR、安装包、性能、隐私和干净系统验收，不能把现有底座视为可发布能力。

## ADR-012：移动 V1 支持受控连续多期票

- 状态：已采用，部分取代 ADR-009；补打票边界于 2026-08-24 补充。
- 决策：Android/iOS V1 支持 1 至 20 期连续单式或多注单式票。单期仍按原精确期号流程；多期只在同一年、三位期次序号可安全连续展开且末期序号不超过 120 时开放。补打票不是独立投注类型，仅在号码、期号、期数、倍数、追加属性和金额完整闭环并通过同一领域校验时放行。复式、胆拖、超过 20 期和跨年度未知序列继续阻断。
- 原因：真实五注多期及补打票探索已经证明彩种、起始期号、期数、倍数、号码和金额可由两端 OCR、人工确认与金额关系共同闭环；逐期复用已有单期双证据和规则引擎，可以在不降低未中奖安全边界的前提下完成当前核心场景。跨年度期号不能只靠字符串加一，必须等待官方期次日历。
- 影响：补打字样或打印来源不能替代任何关键字段，也不自动触发支持或拒绝；票面总金额按投注行、倍数、追加和全部期数严格校验。每一期保存独立结果，发布中或冲突不污染其他期次，尚未发布或整体数据源故障停止本轮后续请求。任一期没有明确结论时不得输出整票未中奖，任一期中奖金额缺失时不得输出整票确定奖金。

## ADR-013：大乐透奖级数据按正式规则失败关闭

- 状态：已采用，2026-08-25 补充浮动奖元级公布口径。
- 决策：`26014` 起的大乐透结果必须恰好包含七个基础奖级；三至七等奖必须整体属于官方同一套固定奖档，一、二等奖已发布追加奖金必须符合对应基本奖金 80% 的元级公布口径。官网分别按整数元公布两个浮动奖金额时，允许 80% 相邻的向下或向上整数元，整除时仍只有一个合法值；浮动奖只采用当期官网金额，客户端不推算，金额不完整不能进入 `FINAL_PAYOUT`。
- 原因：正式规则同时包含命中矩阵、奖池阈值、浮动奖和追加关系，只核对号码或按奖级数组位置取值会在接口漂移、奖档混用或字段缺失时产生错误奖金。
- 影响：数据适配器和 `LotteryPrizeCalculator` 双重校验缺失、重复、未知、混档、负数及追加比例异常；临时派奖没有明确期号规则前继续阻断。

## ADR-014：大乐透历史期使用受控官方 PDF 作为独立证据

- 状态：已采用；iOS Simulator 联网闭环已复测，物理真机完整交互待验收。
- 决策：最新开奖聚合接口不含目标历史期时，只下载主记录绑定的同一期中国体彩网 PDF。Android 使用 PDFBox Android，iOS 使用系统 PDFKit，平台层只提取文本和结构元数据；期号、日期、号码、奖级、固定奖档、追加关系和奖金乘法统一由共享解析器失败关闭校验。
- 原因：历史接口与最新聚合接口无法为非最新期形成两份独立证据，而官方单期 PDF 已在 20 期机器台账中与主 JSON 一致。把语义解析留在共享层可以避免 Android/iOS 因文本顺序不同产生不同判奖口径。
- 影响：PDF 必须是精确期号 URL、最多 1 MB、PDF 1.4、单页、未加密、无表单和固定生产器；原始字节与文本只存在于当前查询调用栈。Android 增加约 2.66 MB Debug APK 体积并承担 Apache-2.0 声明义务，BouncyCastle 不进入运行时。iOS 26.5 Simulator 已在无代理条件下完成公开历史期双证据复测；未来系统信任失败时仍返回网络不可用，不通过证书忽略或不受控代理绕过。

## ADR-015：票样版本基线不早于 2025 年

- 状态：已采用。
- 决策：B0 至 B6 只检索、盘点、调参和验收 2025 年及以后出票的彩票；无法证明出票年份的图片按未知样本处理，不计入数量、白名单、准确率或盲测。
- 原因：销售终端、票面活动区、字段排版和热敏打印质量会随时间变化，2025 年以前的票面不能代表当前 V1 的实际输入分布。
- 影响：2025 年以前的本地或公开图片全部退出当前样本池。2025 年及以后的公开网络图片仍只可用于版式探索、失败关闭和脱敏解析器回归；只有获得样本所有者授权、确认不同物理票、补齐多拍摄条件并完成逐 token 双人真值的实体票，才能进入白名单和准确率验收。V1 开奖规则仍执行更窄的大乐透 `26014` 起、双色球 `2026014` 起边界。

## ADR-016：V1.1 使用跨平台 Room 3 保存结构化票据

- 状态：已采用；依赖与数据契约已于 2026-08-24 冻结，V1.1 已于 2026-08-25 按个人自用双虚拟机基线完成关闭。
- 决策：Android、iOS 使用 Google Maven 已发布的稳定版 `androidx.room3:room3-runtime:3.0.1`、`androidx.room3:room3-compiler:3.0.1`、`androidx.room3` Gradle 插件 `3.0.1`、`androidx.sqlite:sqlite-bundled:2.7.0` 和 KSP `2.3.11`，在独立 `shared:persistence` 模块共享实体、DAO、显式迁移和测试。数据库模式从版本 1 开始，提交 Room 导出的模式文件，禁止破坏性迁移。只保存已经过用户确认和领域校验的数据；用户级导入导出使用格式版本 1 的规范化 JSON 逻辑包和 SHA-256 完整性校验，不直接复制活动中的 SQLite、WAL 或临时文件。
- 原因：二次查询需要稳定复用已确认的投注字段，同时跨平台 Room 可以保持 Android、iOS 的模式和查询契约一致。逻辑导入导出比复制数据库运行文件更容易完成跨版本校验、事务回滚和冲突处理。
- 影响：记录主表保存稳定 UUID、名称、彩种、起始期号、期数、倍数、金额、采集方式、字段来源、创建与更新时间及数据版本，投注行子表按票面顺序保存号码和追加属性；不保存 `originalText`。同一导入 ID 内容一致时明确计为跳过，内容冲突时默认整批不写入，只有用户选择“保留本机并导入其余记录”后才在单个事务中继续，绝不覆盖本机记录。V1.1 导出包不加密，导出前必须明确提示其包含投注信息；Android 继续设置 `allowBackup=false`，iOS 数据库及旁路文件必须排除 iCloud 备份。默认仍不保存票图、OCR 全文、二维码、流水号和官网原始响应；V1.3 的历史开奖持久化需在获得数据授权后另行扩展模式。
- 落地结果：`1.1.0 (3)` 已在锁定 Android 模拟器与 iOS Simulator 完成记录管理、二次查询、系统文件选择器、双向逻辑包迁移和 `1.0.1 (2)` 至 `1.1.0 (3)` 的真实 Room 保留数据覆盖升级。真机矩阵、IPA、商店材料、公开分发和商店升级不属于本决策的当前完成声明。

## ADR-017：V1 公开发布延期，移动验收只使用当前双虚拟机

- 状态：历史决策；双虚拟机固定回归继续有效，V1 关闭、用户真机验收和 V1.1 启动状态由 ADR-018 取代。
- 决策：V1 的公开分发、生产签名、商店上传和发布材料整体延期。当前项目继续完成 V1 功能与稳定性，但 Android/iOS 移动验收只使用 `current-vm-guard.sh` 锁定的当前 Android Emulator 和 iOS Simulator；后续不得为本项目操作 Android 或 iPhone 物理真机，也不把真机矩阵作为当前 V1 完成条件。
- 原因：当前目标是先形成可持续迭代、可重复验证的 V1 内部版本，而不是立即满足公开上架条件。固定双虚拟机可以稳定复现共享规则、网络、OCR 导图、人工校正、页面状态、安装升级和异常恢复，同时避免设备差异与发布账号流程打断核心开发。
- 影响：B6 分为“当前双虚拟机开发验收”和“延期公开发布”两部分；前者可以关闭，后者不再阻塞当前 V1。Simulator 无法证明真实相机硬件、物理设备性能、运营商网络、系统级 OOM/Jetsam 或生产签名，因此文档必须保留这些能力边界，但不得据此要求补做真机验收。既有真机记录只作为历史证据保留，不形成后续执行要求。后续版本仍需单独立项；V1.1 的立项条件现已由 ADR-018 满足。

## ADR-018：按个人自用基线关闭 V1 并启动 V1.1

- 状态：已采用。
- 决策：用户已于 2026-08-24 在 Android 实体设备完成 V1 运行验收，V1 按个人自用内部基线正式关闭，V1.1 获准立项推进。当前产品不发布到应用市场，生产签名、商店材料、公开分发授权和完整真机矩阵不属于 V1.1 的前置条件。
- 原因：当前真实目标是稳定支持用户本人使用并持续迭代，本轮真机结果已证明目标图片、人工确认、查询和测算主流程可用。继续按公开上架标准收束 V1 会消耗开发周期，却不能提升当前个人自用目标的核心价值。
- 影响：V1.1 第一阶段直接冻结 Room 3 准确依赖、数据库模式、迁移策略、备份策略、逻辑导入导出格式、完整性校验和冲突处理，然后进入实现。足量票样、逐 token 双人真值、开奖窗口采样和数据商用授权仍限制对外准确率、可靠性或未来公开分发声明，但不阻塞个人自用版本；人工确认、领域校验、官方证据和失败关闭标准不得降低。未来若改为公开分发，必须单独恢复生产签名、机型矩阵、数据授权、隐私和商店合规计划，不能沿用个人自用关闭结论冒充通过。

## ADR-019：采用独立宿主与 shared 共享模块结构

- 状态：已采用。
- 决策：Android、Desktop 和 iOS 继续使用独立宿主，共享 Compose UI 与应用装配模块从旧模板名 `:composeApp` 迁移为 `:shared`；保留 `:shared:domain`、`:shared:data`、`:shared:persistence`、`:shared:recognition` 业务分层。当前没有 Web 产品目标，不创建官方模板中的可选 `webApp`。
- 原因：2026-08-25 核对的 JetBrains Kotlin Multiplatform 官方共享 UI 模板已使用 `shared`、`androidApp`、`iosApp`、`desktopApp` 和可选 `webApp`。对齐当前命名可以降低新成员理解和官方文档映射成本，但模板命名不应推翻已经稳定、职责清晰的业务模块边界。
- 影响：Gradle project、CI 和 Xcode 构建任务由 `:composeApp:*` 改为 `:shared:*`；Android 与 Desktop 依赖切换为 `project(":shared")`，iOS 继续嵌入名为 `Shared` 的静态 framework。Kotlin 包名、数据库、导入导出格式、应用标识和业务行为均不改变。

## ADR-020：冻结 V1.2 随机选号与导航边界

- 状态：已采用，V1.2 已立项推进。
- 决策：V1.2 支持大乐透和双色球 `1..20` 个相对期次、每期 `1..10` 注，单次方案最多包含 `200` 个投注实例。大乐透所有期次只能复用同一批随机注单；双色球同时支持跨期复用和逐期独立随机。每注按对应号码区域无放回均匀抽样并升序展示，不为排除同一期不同注或不同期次之间的自然重复而重新抽样。
- 原因：边界与 V1 已验证的 20 期上限一致，最多 200 个结果可由惰性列表稳定展示。大乐透没有引入逐期独立随机的明确产品需求；双色球路线图已经冻结两种模式。强制排除注单之间的偶然重复会改变原始随机分布，也会制造没有规则依据的“更随机”错觉。
- 影响：随机方案只表达彩种、相对期次、注数、模式和号码，不包含官方期号、倍数、金额、购买状态或中奖查询入口，并持续展示“不代表预测、不构成购彩建议”。V1.2 不把随机方案写入 V1.1 的已确认票据表，也不修改 Room 模式和导入导出格式；后续如需方案收藏，必须以独立实体、显式迁移和独立视觉语义立项。一级导航调整为“核对、选号、记录”，移动端使用底部导航、宽屏使用侧边导航，为后续走势和 AI 能力保留可扩展目的地。

## ADR-021：V1.3 优先交付跨平台基本走势图

- 状态：已采用并完成实施，2026-08-26；样本范围和会话数据口径已由 ADR-022 更新。
- 决策：V1.3 按“共享领域计算与基本走势图、获授权的历史数据接入与持久化、数学策略与样本外回测”三个阶段推进。首阶段在 `:shared:domain` 定义历史开奖快照、号码区域规格和频次、当前遗漏、最大遗漏计算，在 `:shared` 使用 Compose Multiplatform 实现 Android/iOS 共用的基本走势矩阵；不引入平台专属图表实现或第三方图表依赖。
- 图表口径：大乐透提供前区 `01..35`、后区 `01..12`，双色球提供红球 `01..33`、蓝球 `01..16`；样本范围固定为最近 `50 / 80 / 120 / 300 / 500` 期。左侧展示期号，命中格使用对应彩种颜色的圆点，未命中格展示样本区间内截至该期的遗漏值；号码表头后依次展示出现次数、当前遗漏和最大遗漏，再展示各期开奖行。相邻期同一号码区域的命中点只作低饱和位置连线，不表达因果或预测能力。页面必须显示样本数、起止期号、缺期或冲突状态，并提供无障碍文字摘要。
- 数据边界：首阶段只允许使用测试夹具、明确标记的演示快照，或当前会话内已经合法取得且通过校验的数据完成领域与界面验收；演示快照不得显示为实时官方结果，也不得进入预测输入。未取得允许长期存储、分析和再展示的授权前，不新增历史开奖 Room 表、不批量抓取、不后台轮询、不落盘上游响应，V1.3 不得作为完整版本关闭或对外发布。
- 预测边界：走势图优先，不在首阶段同步包装数学预测。后续预测阶段必须先以独立 ADR 冻结首发策略、参数、时间前推回测、均匀随机基线和可复现快照；若没有稳定优于随机基线，必须如实展示，不得声称提高中奖概率。
- 原因：官方常见的期号与号码遗漏矩阵比普通折线更适合多号码彩票，能够在有限屏幕中同时表达命中位置、遗漏和频次；共享 Compose 与纯领域计算可保证双端口径一致。把数据授权、数据库迁移和预测回测拆开，可以先验证产品交互，同时避免未经授权的长期归档和未经验证的预测宣传。
- 影响：一级导航将增加“走势”目的地；窄屏继续使用底部导航，宽屏继续使用侧边导航。走势图固定单元格尺寸并支持横向滚动，页面纵向滚动，最大辅助字号下不得重叠。真实历史持久化仍需新增 Room 模式、显式迁移、模式快照和升级测试，并与 V1.1 票据实体隔离。

## ADR-022：走势图使用会话内官方最新 500 期

- 状态：已采用并完成实施，2026-08-26。
- 决策：走势图中的“当前往前”统一解释为以对应官网当前最新已发布期为锚点，提供最近 `50 / 80 / 120 / 300 / 500` 期五档真实样本。每个彩种首次进入时由用户操作触发最多 500 期加载，大乐透按官网每页 100 期分页，双色球使用单页 500 期；切换号码区域和样本档位只在当前控制器会话内重新计算。不得用演示快照或猜测期号兜底，失败时显示来源不可用并提供主动重试。
- 数据边界：规范化历史开奖只存在于当前应用控制器会话，不保存官网原始响应，不新增历史开奖 Room 表，不后台轮询，不定时刷新，不跨应用重启长期归档。该会话级低频采样只用于用户当前查看走势图，不代表已经取得公开运营、商业化、长期存储或批量再分发授权。
- 校验边界：大乐透必须校验玩法编号、审核值、开奖状态、公告状态、五位期号、日期年份、前后区数量、范围、唯一性、升序、分页记录数、重复期号和最新期在前顺序；双色球必须校验业务状态、玩法名称、七位期号、详情公告链接、日期年份、红蓝球数量、范围、唯一性、升序、分页记录数、重复期号和最新期在前顺序。任一页面、记录或全局排序异常都失败关闭。
- 原因：10/20/30 期不足以满足手机横屏下的中长期走势观察，静态演示期号也无法证明页面使用了当前真实数据。一次取得完整 500 期后在内存切档，可以同时保证五档口径一致、减少重复官网请求，并避免为尚未获授权的长期存储提前修改数据库。
- 影响：ADR-021 的 `10 / 20 / 30 / 50` 样本范围和演示快照验收口径停止使用。Android 与 iOS 复用同一历史仓库、领域计算器和 Compose 页面；自动化必须动态读取验收时官网最新期号，禁止硬编码会随开奖变化的首末期。数学预测、历史数据持久化和公开分发授权仍不因本决策自动获得批准。

## ADR-023：数学研究采用固定频次遗漏策略与时间前推回测

- 状态：已采用并完成实施，2026-08-26。
- 输入边界：只使用 ADR-022 在当前控制器会话中取得并完成严格校验的同一彩种最近 500 期规范化开奖；不新增网络请求、Room 表、原始响应落盘或跨重启缓存。样本存在空档、冲突或不足 150 期时失败关闭，不生成候选号码或回测结论。
- 首发策略：固定策略标识为 `frequency-omission-ranking-v1`，训练窗口固定为目标期之前最近 50 期。每个号码区域按“窗口内出现次数升序、截至窗口末期的当前遗漏降序、号码升序”排列，取该区域规则要求的号码数量后再升序输出。大乐透生成前区 5 个、后区 2 个，双色球生成红球 6 个、蓝球 1 个；每次只生成一注，不提供热号、冷号或窗口参数切换，也不根据当前样本结果重新调参。
- 回测协议：对已排序历史开奖执行扩展窗口内的滚动前推。第 51 期开始，每个目标期只能使用其前 50 期调用与生产候选完全相同的策略实现；最近 500 期形成 450 个严格样本外目标期。页面展示首末目标期、目标期数，以及主号码、次号码各自的平均命中数。
- 随机基线：均匀无放回选号的每期理论平均命中数固定为 `k² / N`，其中 `k` 为该区域每注号码数，`N` 为号码范围大小。采用精确理论期望而不是有限次蒙特卡洛抽样，避免随机种子和模拟误差影响复现；页面展示策略实测值、随机理论值和差值，不把单次高命中或稀疏奖级作为有效性证据。
- 展示边界：功能统一命名为“数学研究”，候选号码标记为“下一期候选”，持续展示“历史排序不会改变下一期各号码概率，仅供娱乐和研究，不构成购彩建议”。当前阶段只报告本次前推样本的客观差值，并固定说明尚未证明稳定优于随机；不提供购买入口、金额建议、收益承诺、收藏或分享。
- 原因：固定单一、透明、无训练参数的排序策略可以验证生产与回测共用实现、时间泄漏防护和跨平台复现，而不会把复杂模型或事后选择包装成能力。精确均匀随机期望是比有限随机模拟更稳定的基线，也能直接暴露历史排序策略是否只是围绕随机波动。
- 影响：V1.3 可以在不扩大历史数据授权和持久化范围的前提下推进共享领域引擎与双端界面。相同 500 期快照、策略版本和参数必须得到相同候选与回测；任何新增策略、窗口、指标或参数优化都必须另行修改 ADR，并在接触评估结果前冻结。

## 当前冻结状态

V1.1 与 V1.2 已完成关闭；V1.3 已按 ADR-021、ADR-022 与 ADR-023 完成跨平台基本走势图、会话内官方历史开奖、首发数学策略、时间前推回测和双端界面验收，完整版本仅因历史数据授权尚未关闭。后续若变更依赖、数据库模式、备份、导入冲突策略、随机方案持久化或历史开奖持久化，必须新增 ADR，不得在维护中隐式漂移。
