# 分批开发与验收计划

## 1. 执行原则

项目先文档、后开发。每批次必须满足：

```text
输入条件满足
→ 实现批次范围
→ 自动化测试和目标平台验证
→ 形成演示与验收记录
→ 通过闸门后进入下一批
```

禁止为了赶进度绕过人工确认、未知状态拦截、规则版本或真实票样验收。

## 2. 批次总览

| 批次 | 目标 | 主要产物 | 进入下一批的闸门 |
|---|---|---|---|
| B0 | 需求与票样基线 | 文档、票样清单、黄金数据 | 产品边界和样本计划确认 |
| B1 | 四端工程骨架 | KMP 工程、CI、导航、平台能力接口 | 四端构建和基础测试通过 |
| B2 | 开奖查询与规则引擎 | 两源适配、统一模型、现行规则 | 黄金用例对账及发布窗口采样通过 |
| B3 | 移动图片采集与 OCR PoC | Android/iOS 拍照、导入和本地 OCR | 移动端支持样本准确率达到 PoC 门槛 |
| B4 | 票面解析和校正 | 结构解析、校正页、领域校验 | 单式票确认后结构化数据 100% 合法 |
| B5 | 核心端到端闭环 | 查询、中奖测算、结果页、流程状态 | 两种彩票单式端到端通过 |
| B6 | Android/iOS 稳定性与 V1 发布 | 盲测、性能、AAB/IPA、合规材料 | 移动端发布验收标准全部满足 |

工期必须在 B0 真实票样盘点和 B3 OCR PoC 后再估算。当前最大风险不是 KMP，而是票面版式覆盖和 OCR 准确率。

## 3. B0：需求与票样基线

目标：把开发范围变成可验收清单。

任务：

- 固化产品定位为“中奖测算”，不得使用“官方验奖”或“验真”。
- 固化 V1 采集边界：Android/iOS 支持拍照和导入；桌面宿主与导入 PoC 保留到 V1.1 或后续。
- 固化 V1 规则范围：大乐透 `26014` 起、双色球 `2026014` 起。
- 固化 V1 票型范围：受控的 1 至 20 期连续票、单式、多注单式、倍数和大乐透追加。
- 固化票样时间下限：只检索、盘点和验收 2025 年及以后出票的实体票；无法从票面期号、出票时间或来源记录证明年份的图片不得计入样本数量。
- 建立票样台账：省份、销售终端、彩种、票型、玩法、倍数、追加、期数和图片条件。
- 每种彩票先收集 20 至 30 张已失效或已兑奖实体票。
- 建立双人复核的结构化真值和隐私管理流程。
- 固化官网接口字段证据、规则公告和内容哈希。

验收：

- 支持白名单、暂不支持清单和免责声明得到确认。
- 白名单每一行必须包含彩种、省份、销售终端或可辨识终端特征、票面版式版本、票型、追加形态、物理票数量、图片数量、拍摄条件和真值复核状态。
- 探索阶段每种彩票至少 20 张不同物理票，覆盖至少 3 个计划发布省份；无法取得某省份样本时，该省份不得列入 V1 支持白名单。
- 每个白名单版式至少有 5 张不同物理票；不足 5 张的版式只能列为探索项，不能作为发布承诺。
- 白名单、准确率和盲测只统计获得样本所有者授权并完成来源确认的实体票。2025 年及以后的公开网络票图只能用于版式探索、失败关闭和解析器回归，不能替代不同物理票、多拍摄条件或双人真值。
- 样本不得提交 Git；仓库只保留脱敏或合成测试数据。
- 规则版本边界和官方数据源记录可追溯。

停止条件：真实票样不足以识别标题、期号、号码、倍数或追加的版式规律时，不进入自动票面解析开发，先继续样本探索。

## 4. B1：四端工程骨架

目标：建立可持续开发、测试和打包的项目基线。

任务：

- 初始化 Compose Multiplatform 项目和模块。
- 配置 Android、iOS、Desktop 目标与版本目录。
- 建立共享主题、导航和基础页面壳。
- 定义领域模型和平台能力接口。
- 配置 Ktor、kotlinx.serialization 和 Coroutines。
- 建立中文注释规范、静态检查、格式化和测试任务。
- 建立 macOS 与 Windows CI 构建矩阵。

验收：

- Android APK、iOS 模拟器、Windows 开发包和 macOS 开发包能够构建并启动。
- `commonTest`、Android 单元测试、Desktop 测试和 iOS 测试可运行。
- 依赖方向符合 `composeApp → recognition/data → domain`。
- 平台接口有 fake 实现，可在无相机、无 OCR、无网络下演示状态流。

## 5. B2：开奖查询与规则引擎

目标：先走通不依赖 OCR 的确定性中奖测算核心。

任务：

- 实现体彩和福彩 Ktor 适配器。
- 实现 DTO 宽松解析和领域模型严格校验。
- 实现当前测算流程状态和用户触发刷新策略。
- 实现 `DLT_2026_01`、`SSQ_2026_01` 规则。
- 实现单式、多注、倍数和大乐透追加计算。
- 增加手工录入开发页面或测试夹具，以绕过 OCR 验证完整闭环。
- 固化人工最小化的同结构 JSON 契约夹具、官方字段证据摘要和黄金投注结果；不把福彩原始响应提交 Git。

验收：

- 两种彩票可按指定期号精确查询。
- 接口空结果、业务失败、网络失败、字段漂移均映射到正确状态。
- 命中矩阵穷举测试 100% 通过。
- 每种彩票至少选择 20 个 V1 支持期号进行对账，结果 100% 一致；必须覆盖规则生效首期、当前最新期、浮动奖、无人中出奖级、大乐透追加奖、双色球特别规定生效期和退出边界。
- 浮动奖和追加奖金取自当期开奖数据，不使用 `Double`，不本地估算。
- 双色球以 `findDrawNotice` 为主源，特别规定期间能够解析 `fyjCount/fyjMoney`；`forIssue` 不得单独驱动 `FINAL_NUMBERS`。
- 完成两种彩票各连续 6 个真实开奖窗口的发布时序采样，并在次日与官方公告复核；具体协议见本节“发布窗口采样闸门”。
- 任何数据异常都不会输出未中奖。

停止条件：官网接口字段发生无法兼容的变化、现行规则无法用官方黄金数据闭环，或发布窗口采样未通过时，不进入端到端中奖测算。

### 发布窗口采样闸门

这是一次开发验证活动，不是客户端功能。为避免对官网造成不必要请求，采样工具只在受控环境运行，数据只用于内部验证，不进入应用。

- 大乐透连续观察 6 个有效开奖窗口，周一、周三、周六各 2 次；双色球连续观察 6 个有效开奖窗口，周二、周四、周日各 2 次。官方延期或停开不计样本，顺延补测。
- 每场从预计开奖前开始观察，直至首次达到 `FINAL_NUMBERS` 后 60 分钟，并在次日 09:00 复核；同时记录 `FINAL_PAYOUT` 的首次出现时间，金额晚发布不阻塞号码可靠性观察。请求频率必须在实际采样前按官网承受能力和授权情况审批；遇 403、429、5xx 或 WAF 提示立即退避。
- 每次记录北京时间、请求参数、HTTP 与业务状态、耗时、关键缓存响应头、响应 SHA-256、规范化必要字段和状态迁移。福彩原始响应只在内存中完成解析，不写入持久介质；其他证据也不得打包进客户端。
- 发布窗口内单次满足字段条件只进入候选状态；同一期结果至少间隔 60 秒连续两次一致，且与另一个官方页面或接口同号，才能进入 `FINAL_NUMBERS`。超过次日 09:00 的历史期号可在同次用户操作中完成两个官方数据面的交叉核对。
- 必须达到 6/6 场无提前误发布、无错号、无发布后回退或改号；次日均与官方公告一致；必要字段缺失、同一期多记录和无法识别的活动政策均为 0。
- 观察窗口内 HTTP 与业务成功率不低于 99%，连续不可用不超过 2 分钟，403、429 和 WAF 拒绝为 0。若达不到，必须降低频率或更换方案并重新累计连续 6 场。
- 该闸门只能验证观测期内的技术行为，不能替代 API 授权、SLA 或长期稳定性承诺。

## 6. B3：图片采集与 OCR PoC

目标：验证 Android/iOS 本地 OCR 和真实票样可行性，不追求完整 UI。已完成的桌面 OCR 工程底座作为后续版本资产保留，不再作为 V1 闸门。

任务：

- Android CameraX 拍照、Photo Picker 和 ML Kit OCR。
- iOS AVFoundation 拍照、PHPicker 和 Vision OCR。
- 图片临时文件、EXIF 方向、裁切、纠偏和增强。
- 输出统一 OCR 行、文字、坐标和置信度模型。
- 对同一票样进行 Android/iOS 差异评估。
- 保留已完成的 Windows/macOS 文件导入、ONNX Runtime 无遥测工作进程、PP-OCRv5 模型来源锁、可复现转换与数值一致性验证；V1 不继续桌面真实推理和分发验收。

PoC 验收：

- Android/iOS 可拍照并导入 JPG/PNG。
- 彩票图片不上传，分析后临时文件可清理。
- 每种彩票至少使用 30 张 2025 年及以后出票的不同物理票、每张至少 4 种拍摄条件，形成每种彩票不少于 120 张、合计不少于 240 张图片；覆盖至少 3 个计划发布省份。同一物理票的图片不得跨调参与验收集合。
- Android、iOS 每个平台和每个拟进入白名单的“彩种 × 版式”验收单元至少包含 5 张不同物理票、20 张图片；不足该数量的单元只能记录趋势，不能据此判定通过。总量门槛和单元门槛必须同时满足。
- 在每个平台和每个拟进入白名单的版式上，彩种与期号准确率不低于 98%，号码 token 准确率不低于 99%，关键字段错误进入人工校正的召回率为 100%。这是 PoC 进入 B4 的门槛，不是最终发布门槛。
- Android/iOS 本地 OCR 在断网状态下可完整识别，不依赖云端模型或云 OCR。
- 不同 OCR 引擎置信度完成平台校准，不使用一个未经验证的统一阈值。
- 明确无法支持的版式和图片条件。

停止条件：清晰票样的号码 token 准确率仍明显不足，先比较预处理、区域二次识别或替代 OCR 模型，不能用规则静默猜号来掩盖问题。

## 7. B4：票面解析与人工校正

目标：把 OCR 输出可靠转换为用户确认后的领域对象。

任务：

- 实现标题锚点、相对版式和票型分类。
- 实现期号、号码区、倍数、追加、金额等字段解析。
- 实现字段候选值和聚合置信度。
- 实现原图与字段对照的确认页。
- 实现号码球编辑器、投注类型选择、倍数步进器和追加开关。
- 实现金额反算和领域约束校验。
- 未知版式进入 `UNSUPPORTED_TICKET`，不得猜测套版。

验收：

- 支持清单内单式票均可进入确认页。
- 用户确认后生成的 `ConfirmedTicket` 领域校验通过率为 100%。
- 单式号码数量、范围、唯一性、倍数 `1..99` 和票面金额严格校验；多个金额反推候选必须要求用户确认，不得自动任选。
- 复式、胆拖、补打、超过 20 期、跨年度未知序列以及未知追加归属均被明确阻断，不能进入 V1 规则计算。
- OCR 低置信度、金额不一致和范围错误均有明确提示。
- 不支持样本均被拒绝或要求人工修正，不输出错误的最终票据。

## 8. B5：核心端到端闭环

目标：交付第一条可完整体验的业务流程。

任务：

- 串联采集、OCR、确认、开奖查询、规则计算和结果页。
- 多期票按时间顺序逐期查询并保留独立状态，首个未开奖期或整体数据源故障后停止本轮后续请求。
- 展示逐注命中情况、最高奖级、追加奖和税前汇总。
- 展示开奖来源、获取时间、当前数据状态和免责声明。
- 完成无网、未开奖、发布中、上游异常、未知规则和数据冲突页面。
- 实现重新拍照、重新识别、重新确认和重新查询。

验收：

- Android、iOS 均能完成拍照或导入图片到结果的闭环。
- 两种彩票的单期及受控多期单式、多注、倍数与大乐透追加均正确。
- 任一期未完成时不形成整票未中奖；全部期次结论和金额完整后才汇总整票税前奖金。
- 查询前断网、查询中断网、刷新失败和恢复联网场景行为均正确。
- 所有失败状态均不误报未中奖。

## 9. B6：稳定性与 V1 发布

目标：达到公开测试或分发条件。

任务：

- 完成每种彩票 150 至 200 张物理票的盲测规模。
- 完成 Android/iOS 真机矩阵。
- 测试 12MP 大图、旋转、低内存、权限拒绝和网络抖动。
- 完成崩溃恢复、临时文件清理和历史清空。
- 生成并验证 APK/AAB 和 IPA。
- 完成签名、公证、隐私政策、免责声明和官方数据授权确认。

发布验收：

- 达到产品与技术方案中的所有准确率、性能和隐私指标。
- 支持范围内的规则测试和历史对账为 100%。
- 黄金样本误报未中奖数量为 0。
- 安装、升级和卸载不会遗留敏感临时图片。
- 上游接口异常有明确降级，用户可以打开官方公告人工复核。

## 10. V1.1 候选范围

以下内容不属于 V1 发布门槛，在 V1 完成后按产品优先级分别立项：

- 复式投注。
- 胆拖投注。
- 超过 20 期或需要官方跨年度期次日历的多期票。
- Windows、macOS 客户端真实 OCR、ZXing、完整业务闭环和正式分发。
- Windows、macOS 应用内摄像头拍照，是否进入桌面首版需另行评估。
- 更早期号的历史规则。

每项必须有对应真实票样、领域规则、金额校验、UI 校正和盲测标准，不能只增加组合计算逻辑。

## 11. 测试分层

| 层级 | 内容 |
|---|---|
| 领域单元测试 | 命中矩阵、票面金额、奖金、倍数、追加、规则版本、V1 不支持票型阻断 |
| 解析器测试 | OCR 文本到结构化票据、领域约束、未知版式 |
| 数据契约测试 | 官方 JSON 样本、字段漂移、业务错误、空结果 |
| 流程状态测试 | 主动刷新、内容修订、取消、退出流程和状态清理 |
| UI 测试 | 确认、校正、失败状态、可访问性 |
| 平台集成测试 | Android/iOS 相机、选图、权限、文件和 OCR 模型 |
| 真实票样盲测 | 各省版式、终端、光照、折痕、褪色 |
| 安装与发布测试 | Android/iOS 安装包、签名、升级和真机系统 |

线上官网 smoke test 只用于预警，不阻断每次 CI；CI 使用经过最小化的官方字段契约夹具保证可重复性。

## 12. 每批交付物模板

每个批次结束必须提交：

- 本批实现范围和未实现范围。
- 可运行安装包或明确的运行方式。
- 自动化测试结果。
- 真机/桌面验证矩阵。
- 票样数量、分布和盲测指标。
- 已知问题与风险。
- 架构或产品决策变更记录。
- 下一批输入条件是否满足的结论。
