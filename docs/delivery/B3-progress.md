# B3 图片采集与 OCR PoC 进展记录

记录日期：2026-08-24

## 状态结论

B3 已打通 Android 和 iOS 的“系统选图或拍照 → 私有去元数据副本 → 分辨率与像素质量闸门 → 本地 OCR → 共享保守解析 → 人工校正页”纵向链路，并按 ADR-018 纳入个人自用 V1 已关闭基线；Android CameraX 和 iOS AVFoundation 的核心拍照流程已有真机证据。移动端 OCR 已从 Android ML Kit 与 iOS Vision 切换为统一的 PP-OCRv5 mobile 三段 ONNX 流水线，共用检测、方向分类、文字识别、字符字典和后处理。此前 13 张探索图的 ML Kit/Vision 匿名分数只保留为历史基线，不能用于新引擎的阈值或准确率结论。移动端仍可保守拒绝严重整体过暗、严重整体过亮、明显全局模糊、关键印刷内容疑似贴边裁切、明显梯形透视和明显画面倾斜；裁切与透视规则的真实场景准确率、阴影、局部反光、自动旋转和透视校正、PP-OCRv5 真值标注及批量准确率统计仍决定对外自动识别能力声明，但不阻塞 V1.1。

Windows/macOS 已完成系统导图、ONNX Runtime 无遥测工作进程、PP-OCRv5 官方来源锁定、可复现转换和数值一致性验证，但真实推理与分发仍未完成。根据 ADR-011，桌面客户端使用独立路线图另行排期；这些成果继续保留，但桌面未完成项不再阻塞 Android/iOS V1。

当前支持白名单保持为空。本进展不能解释为支持任何省份、销售终端、版式或真实中奖判断。

## 本次已实现

### Android

- 使用 CameraX 提供全屏后置相机取景、闪光灯模式、拍照、真实成片预览、重拍和确认；相机权限按需请求。
- 拍照原始 JPEG 只暂存在应用私有 `camera-captures` 目录，重拍、取消和失败时立即删除；确认后仍需经过统一方向归一、缩放和去元数据重编码，原始暂存文件随后删除。
- 使用系统 Photo Picker 单选 JPG、JPEG 或 PNG，不请求整个媒体库权限。
- 解码后应用 EXIF 方向，将最长边限制为 2048 像素并重新编码为应用缓存内 JPEG；该上限与共享 OCR 解码上限一致，避免 ONNX Runtime Session 常驻后继续分配无推理收益的 4096 像素中间 Bitmap。
- 重新编码后的副本不继承原图 GPS 等 EXIF；缓存目录包含 `.nomedia`，应用启动、流程退出、失败或重新开始时清理临时票图。
- 使用官方 `onnxruntime-android:1.24.2` 在本地执行 PP-OCRv5 mobile 检测、文本行方向分类和文字识别；不下载模型、不上传图片或识别文本。
- 三份 ONNX 从 APK 类路径复制到 `noBackupFilesDir` 后按字节数与 SHA-256 校验并复用 Session；18,383 行字符字典随 APK 打包，ML Kit 代码、依赖和模型资源已移除。
- 使用 `BitmapFactory` 二次幂采样和精确缩放，在后台把私有 JPEG 转为最长边 512 像素的亮度样本；不会把图片路径、像素或质量指标写入日志。

### iOS

- 使用 AVFoundation 提供全屏后置相机取景、闪光灯模式、拍照、真实成片预览、重拍和确认；用户确认前只在内存中持有原始成片数据。
- 使用旋转协调器分别同步实时取景和静态成片方向；确认后复用统一的 UIKit 重绘、缩放和去元数据编码流程。
- 使用 PHPicker 单选图片，不请求整个照片库权限。
- 通过 UIKit 重新渲染并编码最长边不超过 2048 像素的私有 JPEG，从而归一方向并去除原始图片元数据；该上限与共享 OCR 解码上限一致，避免保留无推理收益的大图中间副本。
- 使用微软官方 ONNX Runtime Swift Package `1.24.2` 在本地执行同一套 PP-OCRv5 mobile ONNX；三份模型与字符字典随签名应用 Bundle 打包。
- Swift 宿主只负责连续 Float32 张量与 Session 缓存，Kotlin/Native 通过单次 `NSData` 内存复制交互；检测、方向分类、识别预后处理和坐标归一化与 Android 共用。
- 使用 CoreGraphics 灰度位图上下文，在后台把私有 JPEG 直接缩放为最长边 512 像素的单通道亮度样本；Simulator 已覆盖有效 JPEG 解码、尺寸和亮度输出。

### Windows/macOS

- 使用桌面系统文件选择器单选 JPG、JPEG 或 PNG，不复制原图路径或内容到共享 UI 状态。
- 只读取 JPEG `APP1` 或 PNG `eXIf` 中 TIFF IFD0 的方向字段，不解析 GPS 等其他元数据目录；完整支持 EXIF 方向 `1..8`。
- 使用 ImageIO 限制最长边不超过 4096 像素，并重新编码为应用临时目录内、不携带原始元数据的 JPEG。
- 应用启动时清理异常退出残留，识别失败、流程退出或重新开始时立即删除当前临时票图；路径边界拒绝删除受控目录外文件。
- 接入 `com.microsoft.onnxruntime:onnxruntime:1.29.0` CPU 运行时，并增加只返回版本和执行提供器的 `DesktopOnnxRuntimeProbe`；不加载图片、模型或票面文本。
- 普通桌面 UI 主进程不加载 ONNX Runtime。`DesktopOnnxRuntimeWorkerClient` 使用当前应用启动器创建独立本地子进程，并在进程启动前注入 `ORT_DISABLE_TELEMETRY=1`；子进程探针再次调用关闭遥测 API。
- 工作进程健康检查协议只返回版本和执行提供器，不接收图片路径、OCR 文本或彩票字段；客户端拒绝额外标准输出或错误输出，并在超时后终止子进程，避免静默接受遥测警告或未知状态。
- 桌面入口在创建 UI 前识别内部工作模式；新增 `verifyPackagedOnnxRuntime` Gradle 任务，对 Compose 最终分发启动器、精简 JDK 21 runtime 和分发 JAR 执行父子进程验收。
- macOS arm64 的最终 `.app` 已在父进程明确未禁用遥测时通过验收，确认子进程覆盖为禁用状态后可加载 1.29.0 和 CPU Provider；任务支持 Gradle configuration cache，最终 `.app` 通过 `codesign --verify --deep --strict`。
- 分发 JAR 已核实包含 macOS arm64 动态库、Windows x64 DLL、`Privacy.md` 和 `ThirdPartyNotices.txt`。官方 Maven JAR 仍包含其他平台原生库和 macOS dSYM，当前没有按目标平台裁剪。
- 固定 PaddleOCR `v3.7.0` 的检测、文本行方向和识别三份官方 Paddle 推理模型及 18,383 行字典；源归档和字典均记录 URL、字节数与 SHA-256。
- 固定 macOS arm64、Python `3.9.6`、PaddlePaddle `3.0.0`、Paddle2ONNX `2.1.0`、ONNX `1.17.0`、PyYAML `6.0.3` 和 `packaging 24.2`，所有 wheel 使用哈希锁；转换固定 opset 17、关闭自动升级、开启 checker 并明确使用 `--optimize_tool None`。
- 三份 ONNX 均通过 checker、严格形状推导和 ONNX Runtime Java `1.29.0` CPU Session 加载；使用非彩票确定性合成张量逐元素比较 Paddle 与 ONNX 输出，检测、方向、识别的最大绝对误差分别为 `1.09456266e-7`、`7.30156898e-7`、`7.42673874e-5`，均通过 `rtol=1e-4`、`atol=1e-5`。
- 增加包内 `model-lock.json`、Kotlin 严格解析和路径穿越拒绝测试，以及完全离线、可重复执行的转换工具；普通 Gradle 构建不会联网下载模型。
- 锁定的 ONNX 二进制现已纳入仓库并用于 Android/iOS 应用；延期的 Desktop 仍只装配运行时健康检查，不执行图片或模型推理。

### 共享流程

- OCR 前使用共享检查链依次执行分辨率和像素质量闸门。PoC 分辨率仍要求最短边不少于 720 像素、最长边不少于 1280 像素；尺寸缺失会明确失败，分辨率不足时不会继续解码像素。
- 共享 OCR 将解码图片最长边限制为 2048 像素，检测输入最长边限制为 960 并按 32 对齐；使用 DB 概率图连通域与旋转框提取、unclip 扩张和四角裁切。
- 每个文字框使用 160×80 方向模型判断是否旋转 180 度，再以 48 像素高度和动态宽度执行识别；CTC 后处理统一去除 blank、相邻重复类别和首尾空格，并输出共享 `OcrTextLine`。
- 像素闸门统一分析最长边 512 像素的亮度样本：平均亮度不高于 40 且暗像素比例不低于 35% 时判定严重过暗；平均亮度不低于 235 且高光饱和比例不低于 85% 时判定严重过亮；其余图片的四邻域拉普拉斯方差低于 75 时判定明显模糊。
- 对强 Sobel 边缘使用四倍角合并相差 90 度的水平和垂直主轴；强边缘比例不低于 5%、方向集中度不低于 0.18 且主轴绝对偏角超过 12 度时判定明显倾斜。计算复用同一亮度样本，逐像素循环不调用三角函数。
- 初步裁切规则只分析画面四侧 6% 边框带，并同时要求稳定票面主轴、足量强边缘、黑白印刷过渡和至少两个连续高密度段；它用于拒绝明显切断关键印刷内容，不等同于已经检测到完整彩票轮廓。
- 初步透视规则只比较画面左右半区近竖直强边缘的局部主轴；两侧边缘比例均不少于 3%、集中度均不少于 0.28 且按 90 度等价后的夹角超过 12 度时判定明显梯形透视。方向不足或背景复杂时继续放行，不推断完整彩票轮廓。
- 质量问题按过暗、过亮、模糊、裁切、透视、倾斜的顺序返回，单张图片只提供一个当前最可操作的提示。13 张探索图的正常清晰度最低约为 788、主轴最大偏角约为 7.1 度，确定性强模糊变体最高约为 22、20 度旋转变体最小测得偏角约为 16 度；轻微与极明显梯形合成网格的左右主轴夹角分别约为 1 至 2 度和 12 至 14 度。当前阈值刻意留出间隔，但仍需真实多条件拍摄真值验证。
- 质量闸门拒绝图片时不会调用 OCR，并在错误页出现前清理当前临时图片。桌面端继续只执行分辨率检查，像素闸门属于 Android/iOS V1 范围，不提前扩大延期的桌面工作。
- 两个平台的 OCR 文档统一交给 `ConservativeTicketParser`，不在平台层猜测或修正号码。
- 共享字段区域现保留平台校准前的原始置信度：同一视觉行或跨行字段仅在全部必要 OCR 片段均提供 `0.0..1.0` 合法值时取最低值；任一片段缺失或非法时保持 `null`，避免只统计高分片段后抬高字段分数。
- 当前可采集彩种、期号、逐注号码、倍数、追加、投注期数和票面金额区域的原始分数；OCR 引擎名称与字段分数只存在于当前校正流程内存，不持久化，也不进入确认或查询决策。仅 Debug 包可把解析状态、匿名字段分类和原始分数写入专用平台日志；诊断类型从结构上不包含图片标识、路径、OCR 文本、坐标或字段值，Android 非可调试包和 iOS Release 二进制完全禁用。
- 精确彩种标题仍是首选证据，并选择真正包含关键词且面积最小的原始 OCR 框；标题 OCR 缺失时，只允许“唯一发行机构锚点 + 唯一合法单式号码结构”联合判定并保守取最低原始分数。仅号码结构、机构冲突、结构冲突或结构残缺均要求人工修正。
- 投注期数只在票面明确给出或摘要与合计金额只能恢复出唯一值时生成证据区域；默认单期不伪造期数证据，冲突值保留可用区域并继续阻断解析。
- 分区符漏识别时，只在恰好七个两位号码、数量范围与升序合法、前后区存在唯一明显横向大间隔时恢复 `5+2` 或 `6+1`；侧边纵排文字保持独立，不能再跨越并粘连多注号码。
- 真实识别结果会停留在人工校正页，可修正彩种、期号、号码、倍数、追加和金额；只有完整领域校验通过后才能继续。本记录形成时后续开奖仍为固定演示数据，现已由 B5 接入真实官网查询和本地规则计算。
- OCR 全文、真实号码、期号、路径和 EXIF 不进入日志、测试夹具或文档。

## 本机验证

- Android Debug APK 已使用 `onnxruntime-android:1.24.2` 在项目 `minSdk 24` 下完成构建；包内核对包含三份锁定 ONNX、74,012 字节字符字典和 ORT 原生库，不再包含 ML Kit OCR 资源。通用 Debug APK 因包含四套 ABI 当前约 140 MB，正式 AAB 的按设备下载体积仍需单独测量。
- Android 设备冒烟最初使用 `onnxruntime-android:1.29.0` 时，在当前 ARM64 Android 16 模拟器进入检测模型后执行 SME `rdsvl` 指令并触发 `SIGILL`；因此移动端明确锁定官方 `1.24.2`，Desktop `1.29.0` 不复用到 Android。切换后同一 12MP 非票据合成图实际完成检测、方向分类、识别和共享解析，冷启动约 `3532.1 ms`，随后单次约 `1433.4 ms`，其中 OCR 约 `1415.1 ms`，安全进入人工校正分支。
- iOS Simulator Debug `.app` 已完成完整 Xcode 构建和链接；包内包含三份 ONNX、字符字典和 `onnxruntime.framework`，四个模型资源的 SHA-256 均与 `model-lock.json` 一致。
- 当前 Android 16 ARM64 模拟器使用 12MP 非票据合成图完成 2 次预热和 20 次连续三段真实推理：冷启动 `3745.7 ms`、总耗时 P50 `1326.6 ms`、P95 `1481.1 ms`、最大值 `1589.8 ms`，其中 OCR P95 `1469.5 ms`；20 次均安全进入人工校正分支。
- 当前 iPhone 17 Pro / iOS 26.5 Simulator 的 Debug 应用进程使用同一规格合成图完成 2 次预热和 20 次连续三段真实推理：冷启动 `926.6 ms`、总耗时 P50 `692.8 ms`、P95 `717.5 ms`、最大值 `721.4 ms`，其中 OCR P95 `698.1 ms`；20 次均安全进入人工校正分支。Release Simulator 应用另行验证未启用 Debug 性能入口。
- 上述数据不包含图片或 OCR 文本，只是当前虚拟机开发基线，不是 Release 物理真机 P95，也不能证明真实票准确率。
- 共享测试已覆盖 RGB/BGR NCHW 通道顺序、检测尺寸、DB 连通区域与旋转框、180 度旋转、四角裁切、CTC blank/重复/空格、实际资源哈希及三段合成张量全流水线；iOS Simulator 另以无损上下分色图锁定 CoreGraphics 的从上到下行顺序，避免把文字上下镜像后送入模型。
- 当前 Android 16 与 iOS 26.5 模拟器已使用现有 13 张探索图完成同源、匿名的 PP-OCRv5 结构验收。Android 为 `ready=0 / correction_with_draft=10 / correction_empty=1 / unsupported=2`，共形成 848 行 OCR 文档、80 个安全字段和 18 行安全投注；iOS 为 `ready=0 / correction_with_draft=9 / correction_empty=2 / unsupported=2`，共形成 879 行 OCR 文档、79 个安全字段和 19 行安全投注。两端均无质量拒绝、OCR 质量不足或推理失败，缺损行不进入安全草稿，也未通过规则猜测字符。
- 上述 13 图验收中，Android 总耗时 P50/P95 为 `6534.0/8654.2 ms`，OCR 耗时 P50/P95 为 `6268.4/8410.1 ms`；iOS 总耗时 P50/P95 为 `2259.8/2777.5 ms`，OCR 耗时 P50/P95 为 `2220.8/2743.4 ms`。这些是当前模拟器、Debug 验收入口和逐张冷进程策略下的开发指标，不是物理真机或 Release 性能承诺。
- Android 9 真机已使用一张单期双色球探索样本完成“系统选图 → 私有 JPEG → 离线 ML Kit OCR → 保守解析 → 核对页 → 结束流程”冒烟测试。
- 真机 OCR 未稳定保留精确彩种标题，但发行机构与严格 `6+1` 单式结构形成一致证据后可进入核对页；该结论只验证当前样本的流程可行性，不构成版式支持承诺。
- 当时真机冒烟使用的是只允许结束识别的旧核对页；当前人工校正页已通过共享 JVM 自动化测试，但尚需在 Android 真机上重新执行完整交互与临时图片清理回归。
- Android 9 真机已完成 CameraX 的“拍照 → 重拍 → 再拍 → 使用照片 → OCR 质量阻断”闭环。重拍后 `camera-captures` 立即为空，确认后的原始拍照缓存也被清理；无文字照片返回“图片质量不足”，没有进入 Fake 开奖流程，未发现应用级崩溃或 ANR。

- iOS `iosApp` Scheme 已通过 Simulator 构建；使用个人开发者团队生成的 iPhone 真机包已完成签名、安装、证书信任和启动。应用启动后 `tmp/WinLotteryTicketImages` 为 0 个文件。

## 对外能力声明与后续优化范围

- iOS Simulator 无 AVFoundation 相机设备，不能覆盖横竖屏成片、闪光灯模式和相机拒权；按 ADR-017 仅保留为能力边界，不再列入当前项目验收待办。
- 初步裁切与透视规则的真实场景误拒率与漏检率、完整彩票轮廓、阴影、局部反光及更复杂的局部或运动模糊检测。
- 自动旋转、透视校正、增强候选图和号码区域二次识别；当前倾斜与裁切能力只负责阻断，不会修改原图。
- 移动端 PP-OCRv5 工程接入已完成；真实票逐 token 双人真值、不同拍摄条件批量准确率、置信度校准、低端设备峰值内存、物理真机冷/热 P95 和发布包 ABI/体积验收仍未完成。
- Desktop PP-OCRv5 的 Session 生命周期、图片推理、OCR IPC、ZXing 和 Windows 干净系统文件导入仍未实现，不属于移动端本次替换结果。
- Windows x64 最终分发启动器尚未执行同一父子进程验收；自构建 `--no_telemetry` 制品仍可作为后续纵深防护评估项。
- 当前工作进程只支持运行时健康检查，尚未定义模型 Session 生命周期、图片推理请求、受控临时路径校验、OCR 结果 IPC 和进程异常恢复。
- ONNX Runtime 目标平台裁剪、正式发布包许可证归档、公证和卸载验证。
- 彩种、期号、投注行、倍数、追加、期数、金额的原图区域、解析候选值和原始置信度聚合已经接入 B4，并建立当前 13 图的分平台初步分布；逐 token 真值、正确/错误条件分布、平台分别校准、低置信视觉标记和足量样本仍未完成。
- PP-OCRv5 置信度校准、准确率统计、Android/iOS 物理真机运行时差异评估和真实票连续识别稳定性测试。
- 桌面 PP-OCRv5 资源分发、真实推理、ZXing、Windows 实机与正式安装包验收已延期，不属于移动 V1 闸门。

## 票样与验收差距

- 当前 13 张探索图中，12 张大乐透主要为多期或补打票；补打票已改为在号码、期号、期数、倍数和金额完整闭环后放行。另有 1 张双色球单期票。

- 每种彩票未达到 30 张不同物理票、每张 4 种拍摄条件和至少 3 个计划省份的 B3 门槛。
- 未建立逐 token 双人真值，因此不报告彩种、期号或号码准确率。
- 当前白名单为空，不能据此承诺任何自动识别范围。

## 后续优化候选

以下事项不作为 V1.1 的前置条件；只有对外声明准确率、扩大自动识别范围或对应问题实际影响个人使用时再排期。

1. 建立清晰、倾斜、运动模糊、失焦、欠曝、过曝和正常白底票面的脱敏质量真值集，统计 Android/iOS 误拒率与漏检率后冻结阈值。
2. 扩充彩票边缘、裁切和透视的真实多角度样本并统计误拒与漏检，再评估自动旋转/透视校正、阴影、局部反光与增强候选图；所有失败继续提供单一可操作提示。
3. 只补充可证明为 2025 年及以后出票的大乐透单期基本票、单期追加票、更多受控多期票及当前双色球版式样本，并建立来源授权和逐 token 双人脱敏真值台账。
4. 为当前分平台分布补充逐 token 双人真值和多拍摄条件样本，分别统计正确/错误字段条件分布后再校准阈值、实现低置信字段标记和连续识别性能测试。
5. iOS Simulator 无相机能力时继续验证入口隐藏与导图/手动录入降级；相机横竖屏、闪光灯和拒权不再列为当前项目待办。

桌面恢复开发时，再继续模型资源分发、受控图片 IPC、三段推理与后处理、ZXing、目标平台裁剪、Windows 实机和两端正式分发验收。
