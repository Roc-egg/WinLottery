# V1.1 本机存储与二次查询进展记录

记录日期：2026-08-24

## 状态结论

V1.1 已完成第二个独立进度：跨平台持久化核心落地。`shared:persistence` 已实现 Room 模式、DAO、仓库映射和 Android、iOS、JVM 数据库工厂，不再存在依赖版本、模式、备份、导出格式或导入冲突策略的架构前置项。

本阶段已经完成底层结构化票据保存能力，但尚未接入确认页、记录列表或二次查询入口，因此不宣称用户可见功能完成。后续每个实现阶段必须同时通过 JVM 共享测试、Android 编译和 iOS Simulator arm64 链接检查，并单独提交。

## 依赖与目标锁

- Room 运行时、编译器和 Gradle 插件统一锁定 `3.0.1`，坐标分别为 `androidx.room3:room3-runtime`、`androidx.room3:room3-compiler` 和插件 ID `androidx.room3`。
- SQLite 驱动锁定 `androidx.sqlite:sqlite-bundled:2.7.0`，Android 与 iOS 使用同一 SQLite 实现，避免平台系统 SQLite 版本差异改变查询和迁移行为。
- KSP 锁定 `2.3.11`，项目继续使用 Kotlin `2.4.10`。Room 生成代码必须覆盖 Android、iOS arm64、iOS Simulator arm64 和 JVM 测试目标。
- 版本依据为 2026-08-24 核对的 [Google Maven Room 3 元数据](https://dl.google.com/dl/android/maven2/androidx/room3/room3-runtime/maven-metadata.xml)、[Room 3 Gradle 插件元数据](https://dl.google.com/dl/android/maven2/androidx/room3/room3-gradle-plugin/maven-metadata.xml) 和 [SQLite 元数据](https://dl.google.com/dl/android/maven2/androidx/sqlite/sqlite-bundled/maven-metadata.xml)。升级这些版本必须新增 ADR 并重跑双端持久化回归。

## 模块与数据库模式

- 新建 `shared:persistence`，只负责结构化票据存储、逻辑导入导出和平台数据库构建；它依赖 `shared:domain`，不依赖图片采集、OCR、开奖网络或 Compose UI。
- Room 数据库名固定为 `win-lottery-v1.db`，模式版本从 `1` 开始。模式 JSON 纳入 Git；不得调用破坏性迁移回退。
- `ticket_records` 主表保存：UUID 主键、显示名称、彩种、起始期号、期数、倍数、票面金额、采集方式、五个票级字段来源、创建时间、更新时间和数据版本。
- `ticket_bet_lines` 子表以记录 UUID 与票面行序号为联合主键，外键删除级联，保存前后区号码、追加属性及三个行级字段来源。号码使用 Room 类型转换器编码为 JSON 数组；不手写分隔符协议。
- 读取数据库或导入包形成 `ConfirmedTicket` 后必须再次通过 `TicketValidator`。`BetLine.originalText` 一律恢复为空字符串，数据库中不得出现 OCR 全文、票图路径、二维码、流水号、销售网点、EXIF、开奖结果查询或奖金结论。

## 记录行为

- 只有用户在确认页提交且领域校验为 `VALID` 的票据才能保存。拍照、系统选图和无图手动输入分别记录为 `CAMERA`、`SYSTEM_PICKER` 和 `MANUAL_ENTRY`。
- 每次新的确认流程生成 UUID v4 和默认名称；同一次流程的查询、重试或返回不得重复保存。用户后来再次确认内容相同的另一条记录仍可独立存在。
- 名称去除首尾空白后必须为 1 至 40 个字符。筛选范围为全部、超级大乐透、双色球；文本筛选匹配名称或起始期号。
- 从记录发起查询只复用已保存的 `ConfirmedTicket` 并重新请求当前官方证据，不调用图片采集、OCR 或人工录入。保存记录不包含旧开奖结果查询，因此不存在旧结论覆盖新证据的路径。

## 逻辑导入导出

- 文件扩展名固定为 `.wltickets.json`。格式版本、记录数据版本和 Room 模式版本相互独立，首版均为 `1`。
- 外层 JSON 包含 `payload` 与 `payloadSha256`；哈希为规范化 `payload` UTF-8 字节的 SHA-256 小写十六进制。`payload` 包含固定格式标识、格式版本、导出时间、记录数量和按 UUID 排序的完整记录。
- 导入上限为 5 MiB、2,000 条记录。解析后先核对未知字段、格式版本、数量摘要、UUID、时间、名称和全部领域约束，再校验哈希；任一步失败都不得开启写事务。
- 相同 UUID 且规范化内容完全一致时记为重复并跳过。相同 UUID 但内容不同时先返回冲突摘要，数据库保持不变；用户明确选择“保留本机并导入其余记录”后，才在单个事务中跳过冲突并写入其他记录。V1.1 不提供覆盖本机或自动改 ID。
- V1.1 导出包不加密，因为当前没有账户或跨端密钥管理。导出前必须提示文件包含投注信息；文件只在用户主动操作后交给系统文件选择器，应用不自动上传或同步。

## 备份与迁移

- Android 继续使用清单中的 `android:allowBackup="false"`，数据库不进入系统云备份。
- iOS 数据库放在 Application Support 目录，并对数据库、WAL 和 SHM 设置 `NSURLIsExcludedFromBackupKey`；这些文件不能放入可能被系统主动清理的 Caches 目录。
- 首版没有旧数据库需要迁移。应用覆盖升级时保持模式版本 1 并执行关闭重开测试；未来任何模式版本提升都必须提供显式 `Migration`、前后模式快照和 Android/iOS 升级测试，不允许清库重建。

## 持久化核心完成证据

- `shared:persistence` 已纳入工程，Room 模式版本 1 的 JSON 已提交到 `shared/persistence/schemas`。主表、投注行联合主键、索引和 `ON DELETE CASCADE` 外键均与冻结契约一致。
- 仓库在保存与读取边界重复执行 `TicketValidator`，只接受标准 UUID 和合法名称；读取时恢复字段来源和票面行顺序，保留重复投注行，并始终把 `BetLine.originalText` 清空。
- Android 使用应用私有数据库目录；iOS 使用 Application Support 下的独立目录，并把包含数据库、WAL 和 SHM 的整个目录排除在 iCloud 备份之外。两个平台统一使用 bundled SQLite 驱动。
- 6 组 JVM 真实 SQLite 文件测试已覆盖合法保存与读取、OCR 原文不落库、顺序与重复行保持、非法票零写入、关闭重开、重命名、外键级联删除和清空。
- `spotlessCheck`、JVM 测试、Android 编译、JVM 编译以及 iOS arm64 与 iOS Simulator arm64 编译均已通过。Room 生成的 expect/actual 实现只产生 Kotlin Beta API 编译提示，没有错误。
